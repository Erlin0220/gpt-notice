# gpt-notice v0.7.0 拷问结论

> 状态：全部采用推荐方案
> 日期：2026-07-29

## 1. 页面支持与兼容性

1. 非工作页面不算故障。页面支持状态分为 `initializing`、`supported`、`unsupported`；只有 `supported` 页面才评估 `healthy`、`degraded`、`blocked`。
2. 普通首页和项目主页统一称为草稿页面；`WEB:` 路由称为临时会话；稳定 `/c/<id>` 路由称为正式会话。
3. 页面加载后允许最多 3 秒初始化宽限期。宽限期内禁止派发，但不正式暂停队列。
4. 未知 ChatGPT 路由默认 `unsupported`。只有看起来属于工作页面却缺失关键事实时才判定 `blocked`。
5. `blocked` 不结束任务；任务保持运行并继续观察，但不误报完成、不自动派发。
6. 短暂抖动恢复时不暂停；一旦正式兼容性暂停，恢复后必须人工继续。
7. 不提供绕过兼容性判断的强制自动执行。

## 2. 页面事实与能力

1. 页面状态快照只记录瞬时事实；页面适配评估负责支持状态、兼容性、稳定时间和能力。
2. 适配评估除健康等级外，还必须输出 `canTrackTask`、`canDetectCompletion`、`canAdmitQueue`、`canDispatchQueue`、`canWriteComposer`、`canClickSend`。
3. 内部快照可以持有 DOM 节点；公开快照只能包含可序列化的布尔值、数量、状态和原因代码。
4. 诊断报告不输出助手正文哈希、完整 URL、精确输入长度或真实 Tab ID；使用变化标志、区间和本次报告内别名。
5. 页面实例使用不可逆短标识，便于判断刷新、旧实例和租约竞争。
6. v0.7.0 完成迁移后移除对 `document.querySelector` 的全局覆盖，业务模块显式调用页面适配器。
7. 任务监控器和队列共享页面事实，但保留独立的完成状态机。

## 3. 加入队列按钮始终可用

### 拷问 1：始终可用是否等于始终允许发送？

不是。推荐把“始终可用”定义为：在 ChatGPT 工作页面中按钮始终可见、可点击，并且每次点击都有明确结果；它不等于绕过输入框、路由、兼容性和重复发送安全检查。

### 拷问 2：输入框为空时怎么办？

按钮仍可点击，点击后提示“请输入要加入队列的内容”，不得静默无响应，也不创建空队列项。

### 拷问 3：没有正在运行的任务时能否入队？

可以。用户可以把文本保存为待执行队列项；由于当前页面空闲，新队列默认暂停，不自动发送。用户可以选择“立即执行”或点击“开始/继续”明确启动。

### 拷问 4：页面兼容性受阻时能否入队？

若页面适配器能唯一识别且安全清空活动输入框，可以保存队列项，但队列保持兼容性暂停；若输入框目标不唯一、不可写或无法确认清空，则不得修改输入框，只提示原因。

### 拷问 5：操作进行中是否禁用按钮？

不因业务状态设置 `disabled`。使用内部幂等锁阻止重复点击，按钮显示“处理中”或状态反馈，但保持同一 DOM 节点，避免闪烁和焦点丢失。

## 4. 插件按钮不随回复 DOM 刷新

### 拷问 1：为什么当前会刷新？

当前页面 MutationObserver 在大量外部 DOM 变化时同时触发状态检查和 UI 渲染。ChatGPT 流式输出每个 token 都可能产生 DOM 变化，即使队列 UI 数据没有改变，也会重复更新按钮和状态。

### 拷问 2：是否需要停止观察回复 DOM？

不能。任务完成和队列完成仍需要观察页面。但页面检查和插件 UI 渲染必须拆开：页面变化只安排快照检查，只有派生 UI 模型发生变化时才渲染插件。

### 拷问 3：插件根节点如何保持稳定？

每个页面实例只挂载一次固定根节点和一次事件委托。SPA 跳转不重建；完整刷新自然创建新实例。不得因回复文本变化替换插件根节点。

### 拷问 4：队列列表如何更新？

使用队列项 ID 做增量更新。只有新增、删除、状态、提示或计数变化时更新对应节点；不得在每次检查时重写整段 `innerHTML`。

### 拷问 5：是否需要 Shadow DOM？

暂不引入。稳定挂载、样式命名空间、事件委托和增量渲染已经能解决刷新问题；Shadow DOM 会增加适配和测试复杂度，只有实际发生样式冲突时再评估。

## 5. 队列固定 FIFO，取消上下调整

1. 删除上移、下移按钮和 `moveItem` 领域能力。
2. 队列顺序以加入时间为准，普通自动执行严格 FIFO。
3. 编辑、失败重试不改变原有位置。
4. “立即执行”保留为用户明确选择的例外：可取出选中的等待或失败项先执行，但其余队列项相对顺序保持不变。
5. 删除相关样式、事件分支、测试和静态断言，避免保留无入口死代码。

## 6. 诊断与隐私

1. 诊断事件由 Service Worker 串行写入，不由多个页面直接竞争 Storage。
2. 只记录状态变化和关键动作，不记录每次轮询、每次心跳成功或每个回复 token。
3. 相同页面实例、事件类型和原因代码在短窗口内聚合 `count`、`firstSeenAt`、`lastSeenAt`。
4. 同时执行最多 200 条和最多 7 天两个限制，并在写入或生成报告时惰性清理。
5. 使用本地随机盐和 SHA-256 生成不可逆短会话标识。
6. 报告采用允许列表，不直接序列化内部异常、任务或队列对象。
7. Markdown 和 JSON 基于同一个公开诊断模型；JSON完整表达模型，Markdown提供可读摘要。
8. 清除诊断不删除任务、队列、设置或诊断盐。
9. 诊断 Storage 失败不得影响任务和队列。

## 7. 内部逻辑和插件大小

### 拷问 1：主要问题是压缩率还是重复逻辑？

当前运行资产约 189 KB，其中运行代码、HTML、CSS 和 Manifest 约 156.5 KB，图标约 32 KB；体积本身很小。主要维护成本来自约 69 KB 的队列脚本、重复 DOM 判断、版本化脚本名、全局查询补丁和重复 UI 渲染，而不是下载体积。

### 拷问 2：是否引入打包器和压缩器？

不推荐。为几十 KB 引入构建器、Source Map、产物同步和额外依赖，会增加发布和调试复杂度。继续保留原生 JavaScript、可读源码和零生产依赖。

### 拷问 3：如何真正简化？

1. 页面 DOM 事实只存在于统一适配器。
2. 移除全局 `querySelector` 覆盖和迁移后的重复 helper。
3. 移除队列排序能力及相关分支。
4. 将队列 UI、Storage/租约和运行编排按职责拆开，避免单文件继续膨胀。
5. 将长期运行脚本从 `queue-v060.js` 更名为不带版本号的稳定名称；Storage Schema 继续独立版本化。
6. 诊断、任务和队列使用允许列表公开模型，不复制完整内部对象。
7. 只保留一个 UI 调度器和一个页面检查调度器。

### 拷问 4：如何控制体积回退？

以 v0.6.12 为基线增加自动统计：

- 运行 JS、HTML、CSS 和 Manifest 未压缩总量目标不超过 175 KB。
- 任一运行 JavaScript 文件目标不超过 50 KB。
- Release 只包含运行所需文件，继续排除测试、文档、脚本和开发依赖。
- 超过目标不是机械失败，但必须在发布记录中说明原因并确认没有重复代码或误打包文件。

## 8. 测试和发布

1. DOM fixture 以最小语义结构为主，少量真实结构片段必须彻底脱敏。
2. 测试主要断言公开快照、能力和外部行为，不锁死内部选择器调用次数。
3. 架构测试确保任务和队列不再包含核心 DOM 选择器和错误关键词表。
4. 隐私测试使用 Token、JWT、邮箱、路径、会话 URL 等恶意样本，断言 Markdown 和 JSON 均不泄露。
5. 自动门禁包括语法、单元、静态、无登录 Playwright、打包和体积统计。
6. v0.7.0 正式 Release 前需人工完成普通会话、项目会话、兼容性暂停恢复、Windows 通知和诊断脱敏检查；无法完成时必须明确标记未验证。
