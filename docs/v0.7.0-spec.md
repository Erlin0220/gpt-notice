# gpt-notice v0.7.0 Spec：稳定队列体验、统一页面适配与本地诊断

> 基线版本：v0.6.12  
> 目标版本：v0.7.0  
> GitHub Spec Issue：#16  
> Ticket Map：`docs/v0.7.0-ticket-map.md`  
> 领域词汇：`CONTEXT.md`  
> 相关决策：`docs/adr/0001` 至 `0004`

## Problem Statement

用户依赖 gpt-notice 在当前打开的 ChatGPT 工作页面中监控长时间回答、接收 Windows 通知，并把后续消息保存为队列。现有版本的核心流程已经可用，但仍存在四类直接影响使用体验和维护效率的问题：

1. 任务监控和消息队列分别采集输入框、发送、停止、等待操作、忙碌、错误、消息和复制操作等页面事实，规则容易逐渐不一致。当 ChatGPT DOM 改变时，用户只能看到按钮消失、任务持续运行或队列不继续，无法区分页面仍在执行、当前页面不受支持和扩展兼容故障。
2. ChatGPT 流式输出会持续修改页面 DOM。当前页面观察可能频繁触发队列界面更新，使插件按钮和队列列表发生不必要的刷新、节点重建或点击不稳定。
3. “加入队列”会因为没有活动任务等业务条件而不可点击，用户不能先保存稍后要执行的消息，也不能从按钮直接获得具体原因。队列还提供上移和下移能力，增加了状态分支和界面复杂度，但实际需求只需要按加入顺序执行。
4. 异常主要留在控制台，用户无法导出默认脱敏的诊断资料。与此同时，队列运行模块体积偏大，页面判断、Storage、租约、运行编排和 UI 混合在一起，增加修改风险。

## Solution

v0.7.0 将页面事实统一收敛到一个页面适配边界，并把“页面事实”“页面支持状态”“兼容性评估”和“业务状态机”明确分离。任务监控器和消息队列共享事实与能力，但继续保留各自的任务完成、发送确认、队列完成、稳定窗口和执行租约规则。

在所有受支持的 ChatGPT 工作页面中，“加入队列”入口始终可见、可点击，并且每次点击都返回明确结果。空闲页面允许保存队列项，但新队列默认暂停，不会隐式发送。队列顺序固定为 FIFO，取消上移、下移和内部排序能力；“立即执行”仍是用户明确触发的例外操作。

队列界面在一个页面实例中只挂载一次。ChatGPT 回复的流式 DOM 更新只触发页面检查，不直接触发插件 UI 重绘；界面仅在派生 UI 模型、队列 Storage 或用户操作真正变化时做增量更新。

扩展增加完全本地的诊断事件、公开诊断模型、Markdown 摘要、JSON 下载和 Popup 诊断中心。诊断采用允许列表构造，默认不包含提示词、回复、队列正文、完整 URL、原始会话 ID、Cookie、Token、设备名或本地路径。页面正式进入兼容性暂停后，即使恢复正常，也必须由用户点击继续，不能自动恢复派发。

最后，v0.7.0 删除迁移后的重复页面判断、全局查询覆盖和队列排序逻辑，按职责收敛模块边界，并建立运行资源体积门禁。精简优先减少重复逻辑和状态分支，不引入打包器、压缩器或生产依赖。

## User Stories

1. As an 扩展用户, I want 在 ChatGPT 工作页面始终看到加入队列入口, so that 我可以随时保存下一条消息。
2. As an 扩展用户, I want 加入队列按钮始终可以点击, so that 按钮能够直接说明当前操作为何成功、暂停或失败。
3. As an 扩展用户, I want 输入框为空时获得明确提示, so that 我不会误以为扩展无响应。
4. As an 扩展用户, I want 在当前没有活动任务时仍能保存队列消息, so that 我可以提前准备后续工作。
5. As an 扩展用户, I want 空闲页面保存的队列默认暂停, so that 消息不会在我未确认时自动发送。
6. As an 扩展用户, I want 在页面兼容性受阻时仍能安全保存消息, so that 内容不会因为页面结构变化而丢失。
7. As an 扩展用户, I want 页面兼容性受阻时禁止自动派发, so that 扩展不会重复发送或发送到错误会话。
8. As an 扩展用户, I want 正式兼容性暂停恢复后手动点击继续, so that 页面短暂恢复不会触发意外自动发送。
9. As an 扩展用户, I want 队列严格按加入顺序执行, so that 我能自然预测后续消息顺序。
10. As an 扩展用户, I want 队列中不再出现上移和下移按钮, so that 操作面板更简单。
11. As an 扩展用户, I want 编辑和重试后保持原有顺序, so that 错误恢复不会改变任务计划。
12. As an 扩展用户, I want 保留立即执行能力, so that 我可以明确选择一条消息优先执行。
13. As an 扩展用户, I want 立即执行后其他待执行消息保持原顺序, so that 一次例外操作不会重排剩余队列。
14. As an 扩展用户, I want ChatGPT 流式输出时插件按钮保持稳定, so that 按钮不会闪烁或在点击时被替换。
15. As an 扩展用户, I want 队列面板的展开状态保持稳定, so that 回复生成不会把面板意外关闭或重置。
16. As an 扩展用户, I want 队列列表只在内容真正改变时更新, so that 长回复期间页面操作仍然流畅。
17. As an 扩展用户, I want 看到当前活动页面是否属于受支持的工作页面, so that 登录页或设置页不会被误报为扩展故障。
18. As an 扩展用户, I want 区分页面初始化、受支持和不受支持, so that SPA 切换期间不会过早进入故障状态。
19. As an 扩展用户, I want 区分健康、降级和阻塞状态, so that 我知道扩展还能完成哪些操作。
20. As an 扩展用户, I want 看到具体兼容性原因, so that 我知道应该等待、打开正确页面、复制诊断还是手动继续。
21. As an 扩展用户, I want 一个标签页的兼容故障只影响该页面实例, so that 同会话的其他正常标签不会被错误暂停。
22. As an 扩展用户, I want 持有执行租约的阻塞标签安全释放租约, so that 其他正常页面可以继续竞争执行权。
23. As an 扩展用户, I want 任务在页面阻塞时保持保守运行状态, so that 扩展不会把无法判断误报成完成或失败。
24. As an 扩展用户, I want Popup 分别显示页面兼容性、通知权限、活动任务和队列状态, so that 一个总体标签不会掩盖真正问题。
25. As an 扩展用户, I want 在没有打开 ChatGPT 工作页面时仍能查看本地任务和队列摘要, so that 我仍可以了解扩展状态。
26. As an 扩展用户, I want 一键复制 Markdown 诊断摘要, so that 我可以方便反馈问题。
27. As an 扩展用户, I want 下载结构化 JSON 诊断文件, so that 开发者可以比较页面、任务、队列、租约和通信事件。
28. As an 扩展用户, I want 诊断默认不包含聊天正文和稳定内容哈希, so that 我可以安全分享报告。
29. As an 扩展用户, I want 清除诊断记录但保留任务、队列和设置, so that 排障数据与业务数据互不影响。
30. As an 隐私敏感用户, I want 会话和页面使用不可逆短标识, so that 报告不能直接恢复原始会话信息。
31. As an 维护者, I want 任务监控和消息队列共享同一个页面事实入口, so that 一次适配可以同时修复两条业务链路。
32. As an 维护者, I want 页面适配层只描述事实和能力, so that 任务和队列仍能维护各自的业务状态机。
33. As an 维护者, I want 页面快照具有稳定且独立的 Schema 版本, so that 页面适配可以独立演进和测试。
34. As an 维护者, I want 诊断事件和诊断报告分别版本化, so that Storage 与导出格式可以安全演进。
35. As an 维护者, I want 诊断事件由 Service Worker 统一规范化和写入, so that 多标签并发不会直接竞争同一个 Storage 记录。
36. As an 维护者, I want 相同高频诊断事件自动合并, so that 流式 DOM 和租约续期不会制造大量重复日志。
37. As an 维护者, I want 诊断写入失败不影响任务和队列, so that 辅助能力不会破坏核心功能。
38. As an 维护者, I want 删除全局页面查询覆盖, so that 页面代码和扩展代码之间没有隐式全局副作用。
39. As an 维护者, I want 删除队列排序能力和迁移后的重复辅助函数, so that 状态空间和测试矩阵更小。
40. As an 维护者, I want 页面观察与插件渲染解耦, so that 页面状态检测可以保持敏感而 UI 保持稳定。
41. As an 维护者, I want 任一运行 JavaScript 模块保持可审查的体积, so that 单个模块不会重新演变成难以维护的大文件。
42. As an 发布维护者, I want 自动测试和无登录浏览器回归作为强制门禁, so that DOM 适配与诊断输出可以稳定发布。
43. As an 发布维护者, I want 当前已登录 Chrome 的真实验收结果被诚实记录, so that 外部真人验证失败不会被描述成通过。
44. As an 发布维护者, I want Release 包只包含运行所需文件, so that 文档、测试和开发工具不会增加扩展安装包。

## Implementation Decisions

- 页面适配分为瞬时页面状态快照和页面适配评估。快照只描述可观察事实；评估负责支持状态、兼容性、原因代码和能力标志。
- 页面支持状态使用 `initializing`、`supported`、`unsupported`。只有受支持页面才使用 `healthy`、`degraded`、`blocked` 兼容性等级。
- 工作页面类型明确区分草稿页面、临时会话和正式会话。未知 ChatGPT 路由默认不受支持；只有看起来属于工作页面但缺失核心事实时才判定阻塞。
- 页面适配评估输出细粒度能力，包括任务监控、完成识别、队列保存、输入框写入、自动派发和发送点击能力。业务模块不得仅凭单一健康等级决定全部行为。
- 页面实例内部可以暂时持有 DOM 节点引用；跨模块、跨进程、Storage 和诊断仅使用可序列化的公开快照。
- 输入框诊断只输出是否为空或长度区间，不输出精确正文。助手内容哈希仅用于页面内存中的变化判断，不进入公开诊断报告。
- 页面实例和标签在诊断报告中使用短别名或不可逆短标识，不输出完整 URL、原始会话 ID 或真实 Tab ID。
- 任务监控器和消息队列只消费统一页面事实，不再维护重复的核心选择器和错误关键词。两者继续保留独立的稳定窗口、基线、完成判断和状态机。
- 兼容性弱信号经过短稳定窗口才正式阻塞；路由错误、目标不唯一和强冲突信号可以立即阻塞。
- 正式进入兼容性暂停后必须人工继续。短暂初始化或稳定窗口内恢复不算正式暂停。
- 不提供绕过阻塞的强制自动发送。用户仍可重新检测、复制诊断、取回内容或手动操作 ChatGPT。
- 加入队列入口在受支持工作页面中始终可见、可点击。输入为空时提示；空闲页面成功保存后默认暂停；页面阻塞时只有安全保存能力才允许加入。
- 队列采用 FIFO。删除上移、下移和内部排序能力。编辑、重试保持原位置；立即执行作为显式例外，不改变其余待执行项顺序。
- 插件根节点和事件委托在一个页面实例中只建立一次。页面 MutationObserver 只触发页面检查，不直接触发 UI 重绘。
- 队列 UI 从运行状态派生稳定 UI 模型。只有模型签名、队列 Storage 或用户操作变化时才更新界面，并按队列项 ID 增量更新节点。
- 暂不引入 Shadow DOM。稳定挂载、命名空间样式、事件委托和增量更新是本版本采用的最小方案。
- 诊断事件只记录状态转换和关键动作，不记录每次观察、心跳或成功续租。相同页面、事件类型和原因在短窗口内聚合。
- 诊断事件由 Service Worker 统一规范化、脱敏、裁剪和写入。最多保留 200 条且不超过 7 天，采用写入或生成报告时的惰性清理。
- 会话短标识使用扩展本地随机盐与原生 SHA-256。随机盐与诊断记录分离，清除诊断不删除随机盐。
- 诊断报告采用允许列表构造。错误优先输出固定模块、操作和原因代码；不可避免的自由文本必须经过长度限制和敏感字段过滤。
- Popup 从 Service Worker 获取公开诊断模型。后台按需向当前活动 ChatGPT 标签请求公开快照；无响应时显示页面脚本未响应，不由 Popup 直接访问 DOM 或内部队列正文。
- Markdown 和 JSON 从同一个公开诊断对象生成。JSON 下载使用 Popup 内的 Blob URL，Markdown 复制失败时提供手动复制回退，不新增下载或剪贴板权限。
- 诊断 Storage 与任务、队列和设置分离。诊断损坏优先安全忽略或重建；诊断写入失败不得暂停或破坏核心业务。
- 页面快照、诊断事件和诊断报告分别版本化，不实现诊断 JSON 导入。
- 迁移完成后删除全局页面查询覆盖、重复页面判断、队列排序函数和不再使用的兼容代码。
- 运行职责拆分为页面适配、队列规则、队列 Storage/租约、队列运行编排、队列 UI、任务监控、诊断和 Popup 汇总。拆分目标是减少耦合与重复，不以文件数量本身作为成功标准。
- 不引入构建器、压缩器或生产依赖。运行 JavaScript、HTML、CSS 和 Manifest 的未压缩总量目标不超过 175 KB，任一运行 JavaScript 模块目标不超过 50 KB；超过目标需要明确审查说明。
- 不新增 Chrome 权限，不改变当前页面关闭后停止监控的产品边界。

## Testing Decisions

- 最高测试缝隙是公开页面快照与页面适配评估。测试断言路由类型、支持状态、兼容性、原因代码和能力，不断言内部选择器调用次数。
- 页面适配使用手写最小语义 DOM fixture，覆盖普通草稿、项目草稿、临时会话、正式会话、隐藏旧输入框、多个输入框、控件缺失、忙碌、等待操作和错误。少量真实结构片段必须彻底脱敏。
- 任务监控测试继续验证用户消息确认后创建任务、页面刷新恢复、临时会话提升、跨会话停止、复制操作完成信号和文本稳定兜底；新增阻塞时不得误完成。
- 队列测试验证按钮始终可操作、空输入提示、空闲入队默认暂停、阻塞时安全保存、FIFO、编辑和重试保序、立即执行后的剩余顺序、草稿保护、发送确认、刷新暂停和同会话租约互斥。
- 稳定 UI 使用外部行为测试：在大量助手文本节点和属性变化期间，插件根节点、加入队列按钮和既有队列项节点保持同一实例；只有真实 UI 模型变化才更新展示。
- 架构约束测试验证任务监控器和队列运行不再包含核心页面选择器、错误关键词表、全局查询覆盖、上移、下移和排序能力。
- 诊断测试使用包含邮箱、Bearer Token、JWT、会话 URL、Cookie 字段、本地路径和 API Key 风格字符串的恶意样本，断言公开 Markdown 和 JSON 不包含这些值。
- 诊断测试覆盖事件聚合、数量裁剪、时间过期、损坏 Storage 恢复、随机盐稳定、公开别名、报告版本、清除隔离和写入失败不影响核心业务。
- Popup 测试覆盖健康、降级、阻塞、不受支持、无活动 ChatGPT 页面、页面脚本无响应、复制成功与回退、JSON 下载、清除确认及原设置和任务操作不回退。
- 体积门禁统计实际 Release 会包含的运行资源，而不是整个仓库。超过软目标时测试输出明确审查信息，不通过隐藏压缩或误排除文件达标。
- 自动发布门禁包括语法检查、现有单元和静态测试、新增适配/队列/诊断/Popup 测试、无登录 Playwright 和 Release 内容校验。
- v0.7.0 首次正式 Release 的人工门禁包括当前已登录 Chrome 的普通会话、项目会话、空闲入队、运行中 FIFO、兼容性暂停和人工继续、Windows 通知、诊断导出及人工脱敏检查。
- 当前已登录 Chrome 因真人验证或外部环境无法完成时，必须记录未验证，不得声明真实 E2E 通过。

## Out of Scope

- 关闭 ChatGPT 标签页后继续监控或执行队列。
- 创建后台标签、隐藏窗口、折叠标签组或自动恢复已关闭页面。
- 自动刷新、重新打开页面或绕过真人验证。
- 调用 ChatGPT 私有 API、读取 Cookie 或上传诊断、聊天或队列内容。
- 附件、图片、语音、模型、工具和模式配置队列。
- 队列拖拽排序、上移、下移或任意手动重排。
- 兼容性阻塞后的强制自动执行。
- 远程遥测、错误上报服务、云同步或多设备同步。
- 诊断 JSON 导入。
- Shadow DOM、前端框架、构建器、压缩器或新增生产依赖。
- Chrome Web Store 正式发布。
