## v0.7.1 真实验收修复

真实已登录 Chrome 验收发现并修复两个自动化样本未覆盖的问题：

1. ChatGPT 空输入框不会渲染发送按钮。旧逻辑因此把页面判定为暂不可派发，空闲预存队列点击继续后始终等待。现在启动派发只要求输入框可安全写入，写入文本后再等待发送按钮出现。
2. 首页提升到 `WEB:` 临时会话和正式会话时，队列元数据已经迁移，但清理旧索引会误删目标队列复用的正文 Storage。现在迁移只删除旧索引，保留相同 item ID 的正文。

## 关键结果

- ChatGPT 页面流式输出不再直接触发插件 UI 重绘；插件根节点和加入队列按钮保持同一节点实例。
- 空输入、空闲、运行、暂停和兼容性阻塞状态下，加入队列按钮均可点击并给出明确结果。
- 空闲页面保存队列后默认暂停，不会隐式发送。
- 队列固定按加入顺序执行；立即执行不改变其余待执行项相对顺序。
- 页面只残留隐藏旧输入框时视为兼容性阻塞，不读取或写入该节点。
- 正式兼容性暂停恢复后仍需人工点击继续。
- 首页、`WEB:` 临时会话和正式会话之间迁移时，队列状态和完整正文均保留。
- 诊断报告不包含聊天正文、队列正文、完整 URL、原始会话 ID、Tab ID、Cookie、Token、邮箱或本地路径。
- CI 与自动 Release 均包含锁文件安装、Playwright Chromium 和无登录浏览器冒烟门禁。
- 真实验收不再依赖固定 `Profile 2`，改为当前已登录 Chrome 和 `DevToolsActivePort` 完整 WebSocket 地址。

## 当前已登录 Chrome 真实验收

### 普通会话

- 在全新 ChatGPT 首页预存两条不同消息。
- 入队后默认暂停，人工继续后按 FIFO 依次发送。
- 首页 → `WEB:` 临时会话 → 正式会话两次提升期间，剩余队列和完整正文均保留。
- 两条回复分别完成并生成独立任务通知。
- 流式回复期间加入队列按钮节点引用始终不变。

### 项目会话

- 在项目主页空闲预存消息并默认暂停。
- 注入第二个可见输入框模拟强冲突，队列进入兼容性暂停。
- 移除冲突后队列仍保持暂停，没有自动恢复。
- 人工点击继续后成功发送，并提升到正式项目会话完成回复。
- 项目主页到正式会话迁移期间，按钮和队列状态保持稳定。

### Popup 与诊断

- 扩展版本读取为 `0.7.1`。
- 页面、通知、任务和队列四维状态正常渲染。
- Markdown 与 JSON 来自同一公开诊断模型。
- 使用本轮真实提示词、会话 ID、完整 ChatGPT URL 和邮箱进行泄露检查，均未出现在报告中。

### Windows 通知与打开任务

- Chrome 通知权限、Windows 全局通知和 Google Chrome 通知均为开启状态。
- Windows 通知数据库确认实际生成以下 Toast：
  - 测试通知：`ChatGPT 任务提醒测试` / `通知功能正常。关闭 ChatGPT 页面后不会继续监控。`
  - 普通队列两条完成通知，分别包含问题标题、思考时间和回复首行。
  - 项目队列完成通知，包含问题标题、思考时间和回复首行。
- 真实任务 Toast XML 包含“打开任务”动作。
- 从其他网页触发同一 `OPEN_TASK` 处理后，Chrome 成功聚焦已存在的原项目会话标签，没有重复打开页面。
- Windows 当前未向 UIAutomation 暴露横幅窗口，因此没有把“自动化捕获到可见横幅”写成通过；通知创建、系统入库、内容、动作和标签聚焦已分别验证。
